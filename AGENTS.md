# Filmio engineering guide

## Project overview and source of truth

Filmio is an Android-only Kotlin technical assignment using the TMDB API. The original **Android Technical Assignment-Senior.pdf** is the primary source of truth; `docs/Android Technical Assignment-Senior.md` is a convenience transcription. If this guide, a skill, or starter code conflicts with the PDF, follow the PDF and update this guide.

Required PDF flows: a Compose movie list with infinite scroll and each movie's title, image, and short description; a selected movie's detail screen with extended information such as ratings, votes, and author-related content where available; and search across movies or series after selecting the content type, with controllable request rate. The app uses one activity, handles network errors, and has unit tests for domain, data, and ViewModels. The PDF calls local favorites and offline mode optional; **this project explicitly includes both**. Previously loaded content and local favorites must remain usable offline. Delivery eventually needs a README with setup/design choices and several Git commits.

## Technology stack

These are intended choices for implementation, not claims that the application flows are complete. The repository contains the app and catalog/core modules, shared network error handling, and an initial catalog database schema. The popular-movie endpoint, Room-backed Pager/RemoteMediator, paginated poster-and-summary screen, cached top-level movie details, restorable list/detail navigation, and active-screen reconnect are implemented. List posters are implemented with Coil; detail artwork, credits/review authors, search, and favorite presentation remain to be implemented.

| Technology | Purpose |
| --- | --- |
| Kotlin, Gradle | Application language and build/dependency management. |
| Jetpack Compose, Material 3, AndroidX Activity/Lifecycle/ViewModel | Declarative single-activity UI, lifecycle-aware state collection, and screen state ownership. |
| Coroutines and Flow | Asynchronous Retrofit calls, observable Room/UI state, and controllable/cancelable search input. |
| Retrofit, OkHttp, Moshi converter | TMDB API calls, HTTP configuration/authorization, and JSON-to-DTO conversion. Use one Retrofit converter. |
| Room and AndroidX Paging 3 | Durable catalog/favorites data; Room `PagingSource` and Retrofit-backed `RemoteMediator` support infinite scroll with the database as read source. |
| Koin | Small app-assembled bindings for networking, repositories, and ViewModels. |
| Jetpack Navigation 3 for Compose | App-level screen transitions using stable IDs/route arguments. |
| Coil | Poster/backdrop image loading in presentation. |
| JUnit, `kotlinx-coroutines-test`, MockWebServer | Domain/ViewModel unit tests and data-boundary HTTP tests. Automated testing is limited to local JVM unit tests. |

Room is selected for this project's offline-first behavior. DataStore may be added for a concrete small preference, not catalog/favorites/page-key storage. This is an Android-only project with Retrofit for HTTP; add other libraries only for concrete Filmio requirements.

## Architecture and modules

Use Clean Architecture, MVI, unidirectional data flow (UDF), and a proportionate multi-module structure. Keep dependencies directed inward and compose implementations at the app level. Build modules as functionality is implemented:

| Module | Responsibility |
| --- | --- |
| `:app` | Single activity, navigation host, application configuration, and Koin module assembly. No feature business logic or DTO mapping. |
| `:feature:catalog:domain` / `:data` / `:presentation` | One cohesive film/series catalog feature covering movie list, detail, search, and local favorites. Domain owns models/contracts; data owns TMDB, boundary mapping, Paging mediators, and repository implementations; presentation owns Compose screens and ViewModels. |
| `:feature:catalog:database` | Feature-specific Room storage leaf: entities, `CatalogDatabase`, DAOs, ordered local projections, Room `PagingSource` factories, atomic local writes, exported schemas, persistence tests, and future construction/migrations. No domain/data/presentation or networking dependency. |
| `:core:domain` | Pure-Kotlin shared `Result`, `Error`, and `DataError` contracts. Add other contracts only for genuine reuse. |
| `:core:data` | Kotlin/JVM Retrofit call result handling through `safeCall`. Catalog-specific services/configuration and Android SQLite error translation remain in catalog data; Room belongs to catalog database. |
| `:core:presentation` | Shared Android presentation utilities, `UiText`, and the Filmio light/dark palette and typography used by the app and feature previews. |
| `:core:designsystem` | Reusable theme/components only when actual reuse warrants them. |

Do not create one domain/data/presentation trio per screen: these flows share catalog identity, caching, and favorites. Do not create empty core modules or convention plugins for hypothetical reuse. Gradle includes `:app`, the catalog domain/data/database/presentation modules, `:core:domain`, `:core:data`, and `:core:presentation`. Catalog data depends on its domain, catalog database, and `:core:data`; the database dependency is one-way. Extract other shared behavior only after a concrete cross-feature need appears.

`UiText` lives in `:core:presentation` and supports dynamic strings and Android string resources with optional format arguments. Resolve it in Compose with `asString()` or from a suspending caller with `asStringAsync(context)`; the Android `Context` is explicit outside composition.

## Module dependency rules

- **Domain:** feature domain may use Kotlin, approved pure `:core:domain` contracts, and Paging's non-UI `PagingData` only when needed in a paged repository contract. It SHALL NOT depend on Android UI, networking, JSON/DTO types, Room entities/DAOs, or another feature's data/presentation implementation. Keep business models, repository interfaces, and meaningful business rules here.
- **Data:** feature data SHALL depend inward on its own feature domain. Catalog data owns Retrofit services/DTOs, DTO → entity → domain mapping, repositories, `Pager`/`RemoteMediator`, active request sessions, detail fetching, and error translation. It consumes catalog database's local records/APIs and approved `:core:data` infrastructure. Framework-specific data models SHALL NOT escape into domain or presentation.
- **Database:** catalog database owns Room/KSP configuration, entities, schemas, persistence tests, SQL/DAOs, ordered local projections, atomic local operations, and future construction/migrations. Data passes validated local records into those operations; it SHALL NOT own open-coded Room transactions. Database SHALL NOT depend on catalog domain/data/presentation, Retrofit, Moshi, or `:core:data`. Export Room runtime with `api` for the public database superclass, Paging common for public `PagingSource` queries, and coroutines core for public `Flow` queries.
- **Presentation:** feature presentation SHALL depend inward on its own feature domain and approved shared/core UI abstractions. It SHALL NOT import a feature data/database module or another feature's data/presentation implementation. It renders domain-facing data and sends work through domain contracts.
- **Cross-feature:** feature modules SHALL NOT directly depend on another feature's data or presentation implementation. Use app-level navigation/composition, an explicit public navigation API, or a genuinely shared domain contract when interaction is required. Do not prematurely extract shared abstractions or couple one feature domain to another merely to reuse a model.
- **App:** `:app` may depend on feature presentation entry points and data modules for DI assembly. Add a direct catalog database dependency when DI consumes its construction entry point. App wires implementations to contracts and owns navigation; no SQL or endpoint mapping belongs here. Keep Gradle dependencies explicit so direction is reviewable.

## MVI and UDF conventions

For a screen or coherent flow named `<Feature>`, presentation normally has `<Feature>Screen`, `<Feature>State`, `<Feature>Action`, `<Feature>Event`, and `<Feature>ViewModel`:

- `State` is immutable, durable/current UI state: loading, content, empty, selection, pagination, and recoverable failure/retry information as relevant.
- `Action` is a user/UI intent sent to the ViewModel, including retry and search-type changes.
- `Event` is a one-off effect, such as navigation or a transient message; do not store consumed effects in persistent state.
- `ViewModel` owns state transitions, calls feature-domain contracts, and emits events.
- `Screen` renders state and forwards actions. A small root composable may collect state/events with lifecycle awareness and connect navigation callbacks.

Keep each screen's State, Action, Event, and ViewModel in its own file. ViewModels use a private `MutableStateFlow` named `_state` and expose a public `StateFlow`. One-off effects use a private `eventChannel: Channel<FeatureEvent>` and public `events = eventChannel.receiveAsFlow()`. For subscription-triggered initial work, use `onStart`, `hasLoadedInitialData`, and `stateIn` with `SharingStarted.WhileSubscribed(5_000L)` to avoid repeating the initial request. Keep operation coordination private and expose only state the screen renders. Store explicit Job references only when cancellation/ownership requires them; prefer Flow operators when they already provide the needed cancellation.

State flows **ViewModel → UI**; actions flow **UI → ViewModel**. Pass stable media type and ID between destinations, not DTOs or full response objects. Preserve essential route/query inputs when restoration matters. Let Paging 3 coordinate page loads and retries; do not add a parallel manual paginator. Prevent stale search responses. Choose and document the search debounce/throttle semantics and make the rate controllable. Avoid generic MVI frameworks, base ViewModels, and reducers until repetition justifies them.

## UseCase rules

UseCases are optional. A ViewModel may call its feature-domain repository contract directly for a simple operation. Do not add `GetPagedMoviesUseCase -> repository.getPagedMovies()` or another one-call forwarding wrapper. Add a UseCase only for meaningful business rules, coordination across repositories/operations, business transformations, or duplicated logic across ViewModels.

## Networking and error handling

Follow `.agents/skills/android-data-layer/SKILL.md`, `.agents/skills/android-error-handling/SKILL.md`, and `.agents/skills/android-offline-first/SKILL.md`. Use typed `suspend` Retrofit services in feature data, a shared OkHttp client where useful, and Moshi for DTO conversion. Supply TMDB credentials through non-committed configuration; never hardcode or log them. Map DTOs to Room entities, then domain models at the data boundary. Repositories read canonical data from Room; network refresh writes Room. The paged list uses a Room `PagingSource` and Retrofit-backed `RemoteMediator` with in-memory session continuation and transactional summary-page updates. Load details by stable ID, cache their extended fields, and model absent fields safely. Keep local favorites in separate durable state so refresh cannot erase them. Home displays all stored movies from popular/search requests as one catalog. Search immediately reads local title/original-title matches for the selected media type, including queries never requested remotely; online requests enrich the active results after committing movies to Room. Display the deduplicated union of local matches and active committed remote IDs. Local reads do not wait for the remote debounce. Offline no-match state means no cached matches, not proof that TMDB has no matches. This user-selected policy supersedes exact-query snapshot requirements in the adapted data/offline skills.

`:core:data` currently provides `safeCall` for a typed `suspend` Retrofit invocation. It returns `Result<T, DataError.Network>` using the shared `:core:domain` contract, classifies HTTP, transport, timeout, Moshi decoding failures, and Retrofit's null-body failure, and propagates cancellation and unexpected defects. Catalog data integrates popular-movie pagination through `OfflineFirstCatalogRepository` and `MoviesRemoteMediator`, plus top-level movie details; search remains future work. When catalog list/detail and future search callers use this boundary, write fetched data to Room only after `Result.Success`; on `Result.Error`, keep cached rows and prior transactions intact and pass the typed failure to Paging or screen retry state. The wrapper itself does not retry or write to Room.

`CatalogDatabase` version 1 exports exactly five tables under `feature/catalog/database/schemas/`: canonical `movies`, optional shared-PK `movie_details`, detail-owned ordered `movie_genres` and `movie_production_companies`, and independent `movie_favorites`. Detail existence marks fetched availability; nullable metadata remains unknown. Monetary values use `Long`, collection ID/name are flattened, and no converters are needed. Detail deletion cascades only owned lists; favorite references restrict canonical deletion. Parent writes use non-destructive upserts rather than `INSERT OR REPLACE`. Popular/search refresh adds or updates summaries and preserves older movies, details, and favorites, including on an empty response. No result-set/membership tables, durable page keys, per-movie source/order/page fields, or request-history snapshots exist.

This is unshipped movie-only storage with production DAOs. The unit-only test scope does not include real Room/SQL instrumentation. Persistent construction/DI binding, popular-movie mapping, Room-backed pagination, active reconnect, a poster-and-summary list, cached movie details, and entry-scoped Navigation 3 destinations now exist. Search/author endpoints, domain favorite operations, and detail artwork remain future work. Its initial version-1 export has been revised in place before delivery; released schema changes must increment the version and use preserving migrations. Movie callers use fixed `en-US` and search `include_adult=false`; multiple content locales require separate localized storage. The selected schema omits summary genre IDs, global genre/company lookup tables, country/spoken-language arrays, collection/company artwork, popularity/adult/video flags, response totals, and raw JSON. Series and credits/review-author payloads require later work; companies are not authors. Stored image paths do not guarantee offline image bytes.

`CatalogDatabase` exposes three DAOs organized by operation ownership. `MovieDao` provides a cold whole-catalog `Flow`, deterministic catalog/search `PagingSource` factories, a nullable one-shot summary read, and atomic additive page upserts. Blank search input returns no rows; nonblank search unions literal local matches with committed active IDs. Search text is bound, while only typed `Long` IDs enter a numeric SQL list to support sessions beyond SQLite's older bind limit. `MovieDetailDao` owns transactional snapshot reads/observation and full snapshot replacement across summaries, details, genres, and companies. Its nullable snapshot distinguishes missing movies from summary-only movies with null detail; it sorts owned metadata by stored position. Child writes stay protected inside this DAO, and mismatched owners or constraint failures reject the update. `MovieFavoriteDao` provides paged canonical summaries with added time, observable status, and idempotent add/remove. Favorites sort by added time descending then movie ID ascending; repeated adds preserve the original time, and re-adding after removal records the new time. No generic cache-deletion API or independent child-table DAO is exposed. DAO failures and cancellation propagate; feature data owns recovery/error translation.

Follow the integration handoff in `feature/catalog/database/README.md` and the change design. Data owns active query/type/options, committed remote IDs, and next-page/terminal state in memory; process restart keeps cached content while new remote pagination starts at page 1. An active API-returned movie can be included even if local title matching differs. Query/type changes clear prior remote IDs and obsolete requests cannot publish IDs, errors, or continuation into the new session. Successful local commit precedes ID publication/key advancement; failures retain the prior cache and session retry key. Later Room queries must rebuild/invalidate when active ID parameters change. Database owns local queries and atomic summary/detail writes; networking stays outside transactions. Paging still coordinates load/retry without a parallel manual paginator.

Initial local matching uses literal title/original-title substrings after trimming, ignores ASCII letter case, and preserves other characters literally; percent/underscore are not wildcards. The database builds a bound GLOB pattern with explicit ASCII letter pairs and escaped pattern characters because Android SQLite `lower()` may fold non-ASCII characters. Local results use deterministic `title COLLATE NOCASE ASC, id ASC` ordering, without a TMDB rank/order promise. Empty input issues no remote request. Online search uses controllable debounce independent of immediate local reads; reconnect refreshes the active catalog/query with content still visible, without historical-query refetch or background synchronization. Remove the old one-hour result-set freshness policy. Detail entry always requests the latest API data while stored content remains visible. The injected clock supplies commit timestamps. Pagination ends on empty raw results, reported last page, or accessible page 500 and rejects mismatched response pages; cached row/match counts do not decide completion. Test remote/session behavior with focused unit tests as it is implemented. Review Room queries and atomic operations with the exported schema; fake-DAO unit tests do not prove real persistence or SQL behavior. Never use routine destructive fallback for offline data.

Translate HTTP, connectivity/timeout, rate-limit, and parsing failures centrally at the data boundary into a small domain-meaningful error vocabulary where useful. No `HttpException`, Retrofit `Response`, raw exception text, DTO, or HTTP status handling in presentation. Rethrow coroutine cancellation. Keep diagnostic logs free of credentials. UI state must distinguish uncached offline/unavailable, true empty, loading, cached/stale content, and refresh/append failure. Paging failures must keep cached rows visible and offer retry. Detail recovery uses active reconnect or reopening the destination; search should offer meaningful retry. Use state for recoverable failures and events only for transient feedback.

## Implemented paged movie list

`CatalogRepository` exposes `getPagedMovies(): Flow<PagingData<Movie>>`. `Movie` contains ID, title, nullable overview, optional public `posterUrl` derived by data from the stored TMDB poster path, defaulted shared release/rating/vote/original-title/language metadata, and optional `MovieDetails`. List projections leave `details` null without reading detail tables; only the full detail-observation contract promises fetched availability. Data builds one Pager/mediator per returned stream, maps committed Room summaries to domain movies, and never returns network items directly. Domain also owns framework-free `CatalogPagingException(DataError)` and `ConnectivityObserver` contracts. No forwarding UseCase or artificial domain logic was added.

`MoviesRemoteMediator` launches an initial page-1 refresh, makes sequential APPEND requests, and makes no remote PREPEND request. It uses `safeCall`, fixed `en-US`, nullable response `total_pages`, injected `Clock`, direct DTO mappings, and DAO-owned atomic additive upserts. Null entries are skipped; duplicate IDs use the last supplied occurrence; each batch shares one timestamp. Empty responses retain all storage. Continuation advances only after a validated successful commit and cancellation checks, and stays in memory across local source invalidation. Failed append retries the same page; failed refresh retries page 1 and Paging blocks append until success. Successful refresh starts a new page-1 sequence. End is empty raw results, a supplied total at/below the requested page, or page 500, never mapped/new/local row counts. Canceled or superseded operations cannot publish obsolete continuation; already committed rows remain safe to reload idempotently.

The Pager uses local page/initial sizes of 20, disabled placeholders, and prefetch distance 1. Native Paging cache-boundary scheduling is selected: a local refresh/append that reaches the database end can signal the next remote page before the last displayed row is accessed, including an eager page 2 after the initial page-1 commit. Longer caches load remaining local batches first. No manual paginator or viewport gate is added. A Pager-local callback invalidates the active source after successful nonterminal all-null batches so continuation cannot stall without a table write. `AnchoredMoviePagingSource` delegates reads/invalidation to Room and translates the relative presenter anchor using the first page's `itemsBefore` offset before Room computes an absolute refresh key. This prevents successive refreshes from drifting backward with placeholders disabled; it does not decide remote continuation or query SQL.

Catalog data's narrow observation error handling and internal `safeDatabaseUpdate` map Android `SQLiteFullException` to `DataError.Local.DISK_FULL` and other `SQLiteException`s to `DataError.Local.UNKNOWN`; `:core:data` remains Kotlin/JVM without SQLite dependencies. Expected remote/write failures enter Paging through the safe domain carrier. Cancellation and unexpected defects propagate. Local source load errors use Paging retry and safe generic localized storage feedback; there is no separate Flow-observer recovery framework.

`createCatalogDatabase(context)` uses application context and persistent `filmio-catalog.db`, without main-thread queries or destructive fallback. App assembles database/DAO and BuildConfig-derived configuration with the existing Koin modules in registered `FilmioApplication`; it declares Internet and network-state permissions. Root `/tmdb.properties` is ignored. A nonblank `TMDB_READ_ACCESS_TOKEN` environment value wins over the file; the API key is unused. Missing token builds/startup/local reads work; requests still reach the normal HTTP authorization boundary. Embedded tokens remain extractable from APKs, so credential-bearing generated/build/CI artifacts must remain private. See the root README for setup.

`MovieListViewModel` obtains one stream and uses `cachedIn(viewModelScope)`; recollection reuses its Paging generation instead of starting another initial request. Its private `_state` and public `StateFlow` contain only rendered initial/refresh/append loading, confirmed empty, and localized refresh/append errors. The projection reads source and mediator states separately, preserves source-error precedence, and remembers a completed remote refresh so initial default `NotLoading` signals cannot manufacture an empty result. Movie rows, page counters, DAO values, and retry keys are not screen state. Separate State/Action/Event/ViewModel files remain. Refresh/Retry actions emit `RefreshMovies`/`RetryMovies` through the private event channel; the active root invokes the same collection's `refresh()`/`retry()`. Busy repeated input is guarded; successful loads emit no confirmation.

`AndroidConnectivityObserver` uses application-context default-network callbacks, an initial snapshot, internet plus validated capabilities, and unregisters on collection cancellation. Registration failure ends only connectivity observation, leaving local paging and explicit recovery available. The root collects state and load-state observations with lifecycle awareness and reuses `ObserveAsEvents` for the same Paging collection's commands. Its single event collector owns reconnect observation: the event Flow's `onStart` starts one private ViewModel connectivity Job, and `onCompletion` cancels it immediately when collection stops; ViewModel clearing also cancels the Job. Initial and duplicate available notifications do not refresh; only false-to-true transitions send an unbuffered reconnect command. Suspending delivery waits for receiver readiness during startup, and stopping collection cancels pending sends so resume receives no obsolete reconnect command. Explicit active/inactive actions, undispatched startup ordering, and nested root cleanup are unnecessary. Reconnect refresh can supersede append while cached content remains visible. No background synchronization or historical-query refetch is scheduled.

`MovieListRoot` uses `koinViewModel()` and `collectAsLazyPagingItems()`. The screen uses indexed movie access, stable ID keys, and remembered `LazyListState`, with localized initial/refresh feedback, append loading/error footers, Retry, confirmed empty, a description fallback, and realistic content/error/empty previews. Movie selection emits a stable-ID navigation effect to the app-owned host. Detail artwork, author-related content, search, series, favorite UI/operations, background synchronization, and list freshness remain outside this implemented slice without changing final assignment requirements. Focused local JVM tests use existing-version test-only `paging-testing`, fakes, MockWebServer, and virtual time; manual Room/Compose observations remain separate local verification notes. The five-table version-1 schema is unchanged. The list uses the Pencil design’s FILMIO/Discover header, flat 2:3 poster rows, rating pills, and text-aligned dividers. Coil keeps fixed artwork bounds and a neutral fallback when artwork is missing/loading/failed; offline image bytes are best-effort Coil caching, not guaranteed by Room. The existing Refresh/Retry actions remain available; search and All/Saved controls await their functionality. The green light/dark palette and typography live in `:core:presentation` and are consumed by the app theme and feature previews. App dynamic color is opt-in so the default matches the design.

## Implemented movie details and navigation

`CatalogRepository.fetchMovieDetails(movieId): EmptyResult<DataError>` is a completion-only refresh/commit command for a positive ID. `getMovieDetails(movieId): Flow<Movie?>` is cold local-only observation with duplicate domain values suppressed. Null movie means absent locally; null `Movie.details` in this full projection means summary-only; a present payload means fetched even when optional fields are null and lists empty. Extended value types contain no framework types or cache timestamps.

`OfflineFirstCatalogRepository` consumes the existing `MovieDetailDao` observation and atomic-write operations without changing entities, SQL, schema version, or identity hash. Every `fetchMovieDetails` invocation requests the latest API data without a preliminary cache lookup. Entry and active reconnect fetch while observed cached summaries/details remain visible. The injected clock supplies write timestamps; no periodic work is scheduled.

`TmdbService.getMovieDetails` requests only `movie/{movie_id}` with `en-US`, reusing Bearer authentication and Moshi. Required ID/title and child ID/name decode strictly. The mapper rejects mismatched identity before writing, preserves supplied nulls/zeros/64-bit money, flattens collection fields, omits null children, and deduplicates by last occurrence with contiguous positions. One timestamp updates the summary and detail. The DAO atomically replaces the complete snapshot; favorites and unrelated movies are untouched. Later popular writes update shared summary columns while retaining detail fields, child order, and fetched time. Success follows commit and an activity check; cancellation/defects propagate.

Expected SQLite observation failures throw a framework-free `CatalogStorageException(DataError.Local)` and terminate; a new subscription recovers. Presentation catches only this expected domain carrier, retains last observed content, and gives storage feedback precedence in its single nullable `error: UiText?`. Network completion cannot replace content or clear an unresolved local-read failure. Local observation and fetching proceed independently, so a slow or failed local read cannot block the entry request.

`MovieDetailViewModel` has separate State/Action/Event files, private `_state`, a subscription-triggered `stateIn(WhileSubscribed(5_000L))`, and once-per-instance initial local observation and API fetching. Recollection of a retained ViewModel does not repeat entry work. It owns the local observation Job for recovery, uses a private fetch-in-progress guard, and lets `viewModelScope` cancel fetching. `MovieDetailState` exposes one `isLoading` flag and one nullable `error: UiText?`; cached content stays visible while loading, and `null` means no error. Active reconnect restarts a failed local subscription alongside another API fetch. The event collector owns connectivity observation through `onStart/onCompletion`; only active false-to-true transitions fetch again, and stop immediately releases connectivity observation. `MovieDetailAction` contains only `OnBackClick`. The text screen provides Back, safe unknown metadata, summary-only/offline labeling, and loading/error feedback while content remains visible. Companies are labeled production companies, never authors. Reopening the destination starts another request; detail has no manual fetch controls.

App owns serializable `FilmioRoute.MovieList` / `MovieDetail(movieId)` keys, `rememberNavBackStack`, and saveable-state/ViewModel-store entry decorators. Restored identity creates a local-first detail ViewModel; no movie payload is saved. UI/system Back pop the detail entry and preserve the list ViewModel's cached Paging generation. Duplicate outgoing selection cannot push another active detail route. Koin provides the existing detail DAO and parameterized detail ViewModel. Missing IDs default to zero; nonpositive IDs render safe feedback and Back without repository calls or recovery controls.

Focused JVM tests cover networking, mapping, unconditional fetching, repository/source recovery, fake commit ordering and preservation, ViewModel scheduling/cancellation/reconnect, and list selection. Actual device observations and scenario evidence are recorded in `docs/verification/movie-details.md`; fakes do not prove Room or Compose behavior. Author endpoints/artwork/search/favorite controls remain assignment work.

## Testing strategy

The user selected **local JVM unit tests only** for this assignment. This supersedes earlier guide/skill suggestions for instrumented Room, Compose UI, app startup, and end-to-end tests. Do not add emulator tests, screenshot/mutation infrastructure, or substitute large testing frameworks without a new user request.

- **Domain:** test meaningful business rules when they exist. Current catalog domain has only models and a repository interface; do not test getters or invent UseCases/logic to fill a test category.
- **Data:** use small fakes for repository coordination and MockWebServer for our Retrofit request/DTO boundary. Catalog data uses test-only Mockito subclass mocks to create Android SQLite exceptions without executing SDK stubs; no Android runtime is required. Shared `safeCall` tests own network error classification, decoding failures, and cancellation; avoid repeating them in each feature. Cover cache preservation on failure, requested-page handling, persistence before success, and local observation independently of network work.
- **ViewModels:** inject fake domain repositories and use coroutine virtual time for loading, cached/offline/empty distinctions, retry, duplicate-request prevention, and cancellation. Use Paging presenter/snapshot utilities for generation reuse, continuation, and anchors. Add search/detail/favorite tests only when those flows are implemented.
- **Database/UI:** keep exported Room schemas and manually check the relevant app flows. Do not claim fake-DAO unit tests verify Room SQL, transactions, durable reopen, migrations, or Compose behavior.

Test externally meaningful behavior. Remove placeholders, framework-only checks, duplicate scenarios, and assertions that merely mirror getters or implementation details. Keep fixtures small and dependencies limited to tools used by the retained tests.

## Naming and code conventions

Use `com.example.filmio` as the current package root until a deliberate rename. Name modules `:feature:<cohesive-feature>:<layer>` and packages to match (`feature.catalog.domain`, `feature.catalog.data`, etc.). Use screen-specific names such as `MovieListState`, `MovieDetailAction`, and `SearchEvent` where `<Feature>` would be ambiguous. Put repository interfaces in domain and descriptive offline-first implementations in data. Suffix transport models `Dto` and Room models `Entity`; domain models have neither suffix nor framework annotations. Use media type plus TMDB ID where movie/series identities may overlap. Prefer clear Kotlin names, immutable state, sealed actions/events where useful, and English for code, comments, and project documentation.

## Dependencies, scope, and simplicity

Add dependencies only for a concrete assignment requirement or implemented feature. PDF-mandated technology takes precedence; otherwise prefer focused AndroidX/Kotlin ecosystem choices and avoid overlapping libraries for the same job. This is a technical assignment: favor clarity over cleverness, simple abstractions over generalized frameworks, and adequate performance/resource handling without speculative infrastructure. Avoid unnecessary base classes, wrapper layers, one-line UseCases, and enterprise-scale scaffolding.
